# Stage 102: remove work before attributing it to semantics

Baseline: pinned next `a24e911ba5e571e7adb1c9b5e5151261f9cf101c`, Node 24.19.0.
This pass investigates the remaining overhead identified in stage 101. The
experiment remains unaccepted: neither semantic improvements nor these measured
optimizations establish acceptable final performance or size.

## Retained changes

### Correct a plain selector without recalculating it

When an action ends, an optimistic selector returns to its input. Previously,
even a settled input required a full selector recomputation, despite there
being no input calculation or dependency change to discover. Next restores the
value from its lane slot without that extra pass.

The experiment now uses its existing guarded selected-value setter for this
correction when the input is settled, unheld, and not scheduled for checking or
recomputation, and the output has no computed ancestor. The setter retains its
existing guards for status/errors, comparators, owned children, pending cleanup,
dependency structure, snapshots, attribution, and user-code execution.

The correction still belongs to the action's ordinary update. Descendants run
and can suspend it. The optimization avoids calculating the selector; it does
not commit the selector early. Four new tests cover callback and literal inputs,
scheduled and unscheduled render effects, an async correction, an unrelated
rerender, a late-mounted reader, and cleanup of the previously displayed frame.
Dirty/held inputs and computed owners retain the full path.

### Avoid allocating a closure context for scalar selector writes

`stageSelectedValue` protected function values with
`typeof value === "function" ? () => value : value`. V8's generated bytecode
created a function context at entry, before the callable-value branch. The
allocation profile attributed roughly 790 bytes to this setter across the 16
selector writes in the chain fixture.

The retained setter has no `CreateFunctionContext` instruction; its bytecode
shrinks from 451 to 411 bytes. A separate `selectedLiteral` helper creates the updater wrapper only for
actual callable values. Numeric and other non-callable values take the same
setter path without a captured-variable context. Existing callable-value tests
verify that stored functions are returned rather than invoked. This is in the
experiment's selector code; it does not change the public ordinary setter.

### Investigated but not retained

Two small trials skipped the dependency journal's side-effect-free `park` hook
when its insertion count was zero, and skipped ownership walks when a root's
cached computed ancestor was null. Neither added per-node state. Counts confirmed
that they removed work, but timings did not establish a satisfactory general
tradeoff: the combined trial helped root-owned cycles while the computed-owner
chain was slightly worse. They are archived in `combined-corrected/`, not part
of the retained runtime. Ordinary ownership registration and the full frame
walk remain unchanged.

The first correction trial also exposed an asynchronous error when a guess
expired before its output had ever acquired an extension record. The test
assertions passed, but the runner reported four asynchronous errors and exited
with failure. That trial was not accepted. The corrected fast path requires an
existing extension and otherwise uses the original calculation. Final validation
checks the process exit status and retains both default and JSON reports.

These are optional selector optimizations. No ordinary node fields, version
maps, or additional ordinary synchronous checks are introduced.

## Which costs reflect actual semantic differences?

The production-bundle comparison script exercises these timelines in both
implementations (`results/remaining-cost-stage102/behavior-comparison.mjs`).

### Independent outputs in one action

```ts
const [a, guessA] = createOptimistic(0);
const [b, guessB] = createOptimistic(0);
const details = createMemo(() => a() ? response : 0);
// Separate bindings render [a(), details()] and b().

const run = action(function* () {
  guessA(1);
  guessB(1);
  yield actionFinished;
});
```

While `response` remains pending:

| Runtime | A and details | B |
| --- | --- | --- |
| next | `[0, 0]` | `0` |
| experiment | `[0, 0]` | `1` |

After the response, both show `[1, 10]` and `1`. Next groups these guesses into
one lane. The experiment has separate output publication updates with a shared
action lifetime. Both outcomes are consistent; publishing B independently is a
semantic capability, not proof that next is incorrect in this example.

Some distinct publication state is needed to preserve this independence. The
current **full transaction object and eagerly allocated arrays for every output
are not proven necessary**. Combining every output into one update would remove
the independence; using a more compact representation might preserve it.

### A second proposal after the first one published

Start at zero, publish guess `1`, then guess `2` whose details are pending.
An unrelated signal reruns a second ordinary binding of the optimistic output.
The real production bundles give:

| Runtime | Value and details | Rerun reader's value |
| --- | --- | --- |
| next | `[1, 1]` | `2` |
| experiment | `[1, 1]` | `1` |

Here the difference is correctness: next exposes the proposed guess while the
other reader still displays the committed guess. Separate committed and proposed
output state is required by the experiment's consistency invariant. That does
not prove two **full** computation nodes or all current adoption/commit checks
are required. The input/override split makes the distinction explicit; cheaper
representations remain possible.

### Why not simply borrow every memo input or recycle every update?

An ordinary async-aware memo can emit a raw thenable as an async-iterator value.
An optimistic callback input normalizes that value again. The existing
`layered-shared-input.test.ts` checks this, loading seeds, writable computations,
and refresh behavior. Sharing an explicit synchronous readonly memo is already
supported. Removing the producer indiscriminately changes behavior. A lightweight
normalization record or lazy materialization might replace it, but that has not
been implemented or priced by this pass.

A landed update also cannot simply be reset and reused while stale references
might still identify it: transaction merging, delayed work, and observation
lifetimes use object identity. Recycling needs either proof that all such
references are dead or additional generation checks. No pooling change or
per-read generation check has been added. This is a constraint on a proposed
optimization, not a claim that fresh full transaction allocation is optimal.

## Validation and remaining costs

<!-- validation -->
472 selected scalar tests pass, with 34 baseline/legacy exclusions. The normal
suite reports 5699 passes, including 22 expected failures, with two skips. The scalar
compatibility corpus remains 618 passes and the same 36 classified failures.
The 500-seed overlap campaign passes 30,000 operations. The focused production
suite passes 19 checks with two exclusions. Source and touched-test typechecking pass.
The final runner exits are successful apart from the expected compatibility exit.
Finite tests and microbenchmarks do not establish universal correctness or acceptance.
<!-- /validation -->

The remaining costs are not excused as unavoidable. In particular, the chain
still gives ordinary publication machinery work for the producer and selector,
and independent output updates still allocate complete records and queues.
The common machinery handles errors, async supersession, owned children, and
held dependency frames that a literal selector often does not need. The guard
above shows some of that work can be removed without a new semantic rule.

Three retained-memory runs still measure about 1,063 bytes per callback
boundary versus next's 556 (direct accessor: 1,049 versus 568); the paired-node
representation is unchanged. Both runtimes retain zero disposed-reader payloads.

The next representation-level target is the cost of those independent update
records, especially eager empty queues and rebuilding their node lists. Next
reuses a lane's membership across proposals. The experiment creates a fresh
publication record and grows its list again; the chain profile attributes about
1.2 KB per proposal to adoption. There is room to investigate storage reuse
without reusing the identity of a finished update. Eliminating allocation with lazy storage
would require adjusting direct queue accesses and scope routing; it has not been
ruled out merely because it adds branches. Generic queue/commit improvements
that could also apply to unchanged next must be measured separately rather than
credited as an intrinsic benefit of this experiment.
